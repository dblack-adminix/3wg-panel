# Roadmap 3WG Panel

Этот документ фиксирует ближайшие этапы развития 3WG Panel. Порядок ниже выбран так, чтобы сначала усилить контроль и безопасность, а затем добавлять автоматизацию.

## 1. Audit log

Статус: базовый слой реализован в `v1.3.13`.

Цель: видеть, кто и когда менял состояние панели.

План:

- записывать создание, удаление, отключение и включение peer'ов;
- записывать смену категории peer'а;
- записывать создание, изменение и удаление пользователей;
- записывать выпуск и удаление API-ключей;
- записывать изменение monitoring settings;
- хранить actor, action, object_type, object_id, timestamp, IP/request metadata и краткий JSON context.

Ожидаемый результат: администратор может восстановить историю действий без просмотра shell logs.

## 2. Страница Audit / Logs

Статус: базовая страница `/audit` реализована в `v1.3.13`; расширенные фильтры и экспорт остаются следующим шагом.

Цель: дать администратору удобный UI поверх audit log.

План:

- отдельный раздел `/audit`;
- фильтр по дате, пользователю, действию, peer, protocol;
- компактная таблица событий;
- раскрытие деталей события;
- экспорт в CSV/JSON.

## 3. Backup / Restore из UI

Статус: базовая страница `/backups` реализована в `v1.3.14`.

Цель: сделать штатные операции с backup доступными из панели.

План:

- страница `/backups`;
- создание backup вручную;
- список последних backup;
- скачивание backup;
- проверка размера и даты;
- restore только с явным подтверждением и предупреждением.

## 4. История System Status

Статус: базовые snapshots и графики 1 час / 24 часа / 7 дней реализованы в `v1.3.15`.

Цель: System Status должен показывать не только текущий момент, но и историю.

План:

- сохранять snapshots CPU, memory, disk, network, containers в SQLite;
- графики за 1 час, 24 часа, 7 дней;
- агрегировать старые точки, чтобы база не росла бесконечно;
- показывать пики CPU/RAM/network.

## 5. Health diagnostics

Статус: базовая страница `/tools/health` и API `/api/node/diagnostics` реализованы в `v1.3.16`.

Цель: быстро понимать, почему сервер или протокол не работает.

План:

- проверка контейнеров `3wg-panel`, `amnezia-wireguard`, `amnezia-awg2`;
- проверка Docker socket;
- проверка protocol config path;
- проверка `wg show` / `awg show`;
- проверка endpoint ports;
- проверка Caddy/reverse proxy;
- проверка DNS и публичного endpoint host;
- понятный список `OK/WARN/FAIL` с подсказками.

## 6. Улучшение страницы peer

Статус: базовая диагностическая карточка peer реализована в `v1.3.17`; график по peer, заметки и расширенные предупреждения остаются следующими шагами.

Цель: страница клиента должна быть главным местом диагностики конкретного peer.

План:

- last handshake и age;
- RX/TX график именно по peer;
- кнопка диагностики peer;
- заметка/описание клиента;
- дата создания, создатель, категория;
- источник protocol-контейнера;
- предупреждение, если VPN online, но ICMP ping не отвечает.

## 7. Expiration / auto-disable

Статус: базовые сроки действия peer и auto-disable реализованы в `v1.3.18`; фильтр "истекают скоро" и массовое продление остаются следующим шагом.

Цель: ограничивать peer'ы по времени.

План:

- поле `expires_at`;
- отображение "истекает через N дней";
- автоматическое отключение истёкших peer'ов;
- фильтр "истекают скоро";
- ручное продление.

## 8. Traffic limits

Статус: базовые total traffic limits на peer реализованы в `v1.3.19`; накопительные counters по peer в SQLite реализованы в `v1.3.20`, dashboard patch синхронизирован в `v1.3.21`; лимиты по пользователю и reset counters остаются следующим шагом.

Цель: ограничивать пользователей или peer'ы по объёму трафика.

План:

- лимит RX/TX/total на peer;
- лимит RX/TX/total на пользователя;
- предупреждение при приближении к лимиту;
- auto-disable при превышении;
- отображение прогресса лимита в UI.

## 9. Telegram notifications

Цель: администратор должен получать важные события без входа в панель.

План:

- новый peer создан;
- peer отключён/удалён;
- контейнер упал;
- новая версия доступна;
- backup создан или завершился ошибкой;
- превышение traffic limit;
- истечение peer.

## 10. Обновление из UI

Цель: сделать обновление понятным и управляемым.

План:

- показывать текущую версию;
- показывать latest GitHub tag;
- показывать changelog;
- запускать update script из UI только для super admin;
- показывать live output обновления;
- обязательно создавать backup перед update.

## 11. API keys documentation и API surface

Цель: внешние интеграции должны понимать, что можно делать через API-ключ и как безопасно его использовать.

План:

- отдельная документация `docs/API_KEYS.md`;
- примеры `curl`;
- список endpoint'ов;
- описание прав и ограничений;
- правила хранения и ротации token.
